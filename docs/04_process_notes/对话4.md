# 二、产品核心体验

我们围绕“出门请求”细化了小芽如何促使用户走出室内：

441. **小芽需要晒太阳**
 它会通过光照传感器判断自己是否见到了真实阳光。 

442. **小芽需要被带着走**
 它会通过 AtomS3R 自带 IMU 判断自己是否被拿起、移动、带出门。 

443. **小芽未来需要接触城市声音**
 后续可以用麦克风判断环境是安静还是热闹，甚至进一步识别鸟鸣、车流、人群等城市声音。 

444. **小芽给用户低门槛任务**
 比如： 

    - 3 分钟阳光 

    - 听一分钟城市声音 

    - Color Walk 

    - 找一种绿色物品 

    - 下楼走一圈 

    - 发现附近新变化 

445. **小芽不是让用户沉迷 AI，而是把用户带回真实世界**
 这一点后来成为项目最核心的表达。

# 六、DLight 光照传感器调试

我们专门测试了 DLight / BH1750。

一开始 Serial Monitor 报错：

```Plain Text
I2C transaction failed
unexpected nack detected
```

后来通过 I2C Scanner 确认传感器地址是：

```Plain Text
0x23
```

之后成功读取 lux 数据。

你实测的数据包括：

```Plain Text
手捂住：0 lux
桌面平放：约 447 lux
手电筒 20cm：约 530 lux
手电筒 10cm：约 915 lux
```

基于这些数据，我们设置了光照阈值：

```Plain Text
0–50 lux       NEED_SUN
50–500 lux     INDOOR
500–800 lux    BRIGHT
800+ lux       SUNLIGHT
```

然后写出了 **DLight 控制 M5 彩色植物状态版代码**：

```Plain Text
遮住传感器 → 小芽暗绿色、低头
桌面光 → 小芽正常或明亮
手电筒照 → 小芽亮绿色、有太阳光点
```

# 七、AtomS3R 自带 IMU 运动检测

我们接着测试了 AtomS3R 自带 IMU。

最开始判断三种状态：

```Plain Text
STILL
MOVING
WALKING
```

但你发现三种状态在走动时会频繁切换，不够稳定。

于是我们简化成两态：

```Plain Text
STILL = 静止
ACTIVE = 被拿起 / 移动 / 走动 / 晃动
```

并加入状态保持时间：

```Plain Text
检测到 ACTIVE 后保持约 1.5 秒
```

这样就不会因为瞬时加速度变化而频繁跳回 STILL。

最后 IMU 两态检测跑通：

```Plain Text
放桌上 → STILL
拿起来 / 走动 / 晃动 → ACTIVE
```

# 九、OLED 文案逻辑预备版


4168. **AI 让用户与植物建立情感连接**
 用户记住的不是传感器，而是小芽说过的话。

# 十一、后端与 Wi\-Fi 逻辑

我们解释了为什么后续需要后端：

```Plain Text
AtomS3R 负责硬件感知和显示
电脑 Flask 后端负责 AI 文案生成
大模型负责生成植物语言
```

后端的作用是：

```Plain Text
接收 lux / motion / sound
↓
组装 prompt
↓
调用 AI
↓
返回一句植物语言
↓
OLED 显示
```

同时解释了为什么 AtomS3R 和电脑需要在同一个 Wi\-Fi 下：

```Plain Text
因为 Flask 后端运行在你的电脑上，
AtomS3R 需要通过局域网 IP 找到你的电脑。
```

也解释了为什么不能用：

```Plain Text
127.0.0.1
```

因为在 AtomS3R 上，127\.0\.0\.1 指的是它自己，而不是你的电脑。


```Plain Text

→ The city sounds alive today.

SUNLIGHT + ACTIVE + QUIET
→ It feels peaceful outside.

NEED_SUN + STILL + QUIET
→ Everything is very still.
```

但我们也明确了：

```Plain Text
环境音是体验增强层，不是当前 MVP 的核心闭环。
```

当前核心闭环已经是：

