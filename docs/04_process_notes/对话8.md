## 1. 本对话框的核心主题

这个对话主要围绕“出走小芽 City Sprout”的产品方向、软硬件架构、AI功能边界、公开仓库安全、PRD文档和后续交接展开。

项目已经从早期的“真实城市树感知装置”收敛为：

> 一个可携带的 AI 小植物，通过光照、动作、声音、环境等传感器感知自己是否长期待在室内，并用植物口吻邀请用户带它出门、晒太阳、听城市、收集颜色、记录散步。

本对话后半段进一步明确：项目不再只是硬件 Demo，而是要同步推进软件端 APP、后端 AI 服务和硬件小芽。

## 2. 已确认的产品方向

### 2.1 项目一句话

出走小芽是一棵想见真实世界的 AI 小植物。

它通过硬件感知环境，通过后端和 AI 理解状态，通过 APP 记录和呈现散步体验。

用户不是被提醒运动，而是在照顾一棵想见阳光、想听城市、想收集颜色的小芽。

### 2.2 产品不是健康打卡

反复确认过的产品边界：

- 不做运动打卡器。
- 不做步数 KPI。
- 不用“你应该运动”这种表达。
- 不用责备、监督、焦虑式提醒。
- 小芽的表达应该像植物在说自己的感受。

好的语气方向：

- “我今天还没有见到真正的阳光。”
- “我们可以去找一点绿色吗？”
- “我好像听到了鸟鸣。”
- “阳光落在我的叶子上了。”

不好的方向：

- “你已经太久没出门了。”
- “你应该运动。”
- “请完成今日任务。”

## 3. 当前硬件架构

### 3.1 主控和模块

当前硬件方案已经稳定为：

```text
AtomS3R + Atomic Voice Base
↓
PaHUB
├── Port 0: DLight 光照传感器
├── Port 1: Unit OLED
└── Port 2: ENV-Pro 环境传感器
```

当前硬件模块职责：

| 模块 | 作用 |
|---|---|
| AtomS3R | 主控、Wi-Fi、程序运行、内置彩屏显示小芽 |
| Atomic Voice Base | 麦克风、扬声器，后续用于录音和播放语音 |
| DLight | 读取 lux，判断缺光/阳光 |
| OLED | 黑白文字屏，显示状态和短句 |
| ENV-Pro | 温湿度、气压、空气质量趋势 |
| AtomS3R 内置 IMU | 判断 still / moving / walking |
| PaHUB | 让多个 I2C 模块同时连接 |

### 3.2 显示分工

AtomS3R 自带彩屏：

- 显示彩色小芽动画。
- 显示小芽形态和极简状态。
- 不显示大量文字。

OLED 黑白屏：

- 显示状态。
- 显示植物说的话。
- 显示少量传感器摘要。
- 英文短句优先，中文后续再处理。

## 4. 已讨论和处理过的硬件功能

### 4.1 光照检测

DLight 光照传感器已作为核心输入。

状态判断方向：

```text
lux < 50      -> wilted
lux < 300     -> need_sun
lux >= 300    -> sunlight
```

阈值只是初版，需要根据真实室内、窗边、室外阴天、室外阳光继续校准。

### 4.2 IMU 动作检测

项目中出现过 `imu_motion_test.ino`，用于光照 + 移动检测。

动作状态用于判断：

- still
- moving
- walking
- picked up

运动状态可以覆盖光照状态，例如设备正在被带着走时进入 `STATE_WALKING`。

### 4.3 声音环境检测

声音功能被拆成两层：

第一层：硬件端声音变化检测。

- 判断声音是否安静。
- 判断声音波动是否变大。
- 辅助判断室内/室外。
- 不要求识别“具体是什么声音”。

第二层：后端或 APP 上传录音后做声音内容识别。

- 识别车流、人声、鸟鸣、风声等。
- 用于 Sound Walk 和散步日记。

结论：

```text
硬件实时判断声音变化：本阶段可做
硬件实时识别具体声音内容：不建议本阶段强做
APP 录音上传后端识别声音类型：可以纳入软件端本次目标
```

### 4.4 Atomic Voice Base

讨论过 Voice Base 的两个方向：

1. 麦克风输入：用于环境声音变化检测或录音。
2. 扬声器输出：播放提示音或语音。

已明确：

- 基础状态语音可以做成预设音频。
- 少量语音可以存到硬件 Flash / LittleFS / SPIFFS 中。
- 不建议把大量动态 AI 语音都永久存到硬件里。

推荐方案：

```text
基础状态语音 -> 存硬件本地
Color Walk / Sound Walk / 日记语音 -> APP 或后端播放
```

## 5. AI 功能边界的关键调整

本对话中有一个非常重要的产品判断：

> 高频、重复、状态明确的反馈，不一定需要大模型；可以用文案库。大模型应该用在输入复杂、结果不固定的地方。

### 5.1 适合文案库的功能

这些状态大部分用户都会经历，传感器数据也相似：

- 室内静止
- 缺光
- 想晒太阳
- 被拿起
- 正在走路
- 看到阳光
- 声音变丰富

这些可以用规则 + 文案库生成。

示例：

```json
{
  "need_sun": [
    "我今天还没见到真正的阳光。",
    "可以带我去窗外看看吗？",
    "我有点想晒太阳了。"
  ],
  "walking": [
    "我们是在出门吗？",
    "外面的空气好像不一样了。",
    "我感觉自己正在路上。"
  ],
  "sunlight": [
    "阳光落到我的叶子上了。",
    "我好像又活过来了。",
    "这里的光真好。"
  ]
}
```

### 5.2 适合大模型的功能

大模型主要用于复杂理解和总结：

| 功能 | 是否适合大模型 | 原因 |
|---|---|---|
| 基础状态短句 | 不优先 | 高频重复，文案库更稳 |
| Color Walk 图片分析 | 适合 | 每张照片内容不同 |
| Sound Walk 声音识别 | 适合 | 录音内容不同 |
| 散步日记 | 很适合 | 需要综合多种输入 |
| 个性化长期总结 | 适合后续 | 需要历史记忆 |

推荐架构：

```text
硬件实时状态
↓
规则判断 state
↓
文案库返回短句
↓
OLED / APP 首页立即显示

复杂任务数据
照片 / 录音 / 散步记录
↓
调用大模型
↓
生成图片总结 / 声音总结 / 散步日记
```

## 6. 后端方向

### 6.1 Flask 后端

当前后端核心接口仍然是：

```text
POST /plant
```

硬件上传：

```json
{
  "state": "walking",
  "lux": 523.33,
  "motion": "walking",
  "sound_level": 0.42,
  "sound_range": 0.31,
  "temperature": 26.1,
  "humidity": 61.2,
  "pressure": 1011.8,
  "iaq": 0
}
```

后端返回小芽短句。

后续 APP 可以通过：

```text
GET /latest
```

获取最新状态和文案。

### 6.2 云服务器和本地后端

讨论过云服务器：

```text
http://111.229.81.45:5000
```

也讨论过本地电脑后端。

重要原则：

- 云服务器地址属于敏感信息，不应直接提交到公开 GitHub。
- API Key 不能出现在仓库。
- Wi-Fi 名称和密码不能上传。
- 使用环境变量或本地 secrets 文件管理。

### 6.3 环境变量和公开仓库

后端应使用：

```text
.env
.env.example
```

Arduino 端应使用：

```text
arduino_secrets.h
arduino_secrets.example.h
```

其中：

- `.env` 不上传。
- `arduino_secrets.h` 不上传。
- example 文件上传，给别人照着填写。

### 7.1 首页 Home

首页目标：

- 展示小芽当前状态。
- 展示小芽形象。
- 显示上一次出门时间。
- 显示小芽刚刚说的话。
- 显示传感器摘要标签。
- 给出当前推荐任务。

示例：

```text
有点蔫了
我们上一次出门是5天前

今天是晴天，我们去周围找5种绿色的东西，如何？
```

### 7.2 小芽状态同步到 APP

用户提出：小芽每次感知到不同状态后说的话，希望显示在 APP。

建议实现：

```text
硬件检测状态
↓
POST /plant
↓
后端返回文案
↓
OLED 显示短版
↓
APP 首页显示完整版本
```

### 7.3 Color Walk

Color Walk 是软件端重点功能。

用户可以：

- 打开 Color Walk。
- 拍照。
- 上传照片。
- 让大模型识别照片中的颜色和内容。
- 小芽根据图片做总结。

示例总结：

```text
我看到你已经收集5种绿色了，真棒。
```

需要识别：

- 主色
- 绿色数量
- 是否有树、叶子、草、花、天空、街道等
- 当前任务进度

### 7.4 Sound Walk

Sound Walk 讨论后结论：

- 本次可以加入 APP 录音上传 + 后端识别声音类型。
- 不建议本次强做硬件端实时声音内容识别。

声音识别目标：

- 车流
- 行人交谈
- 鸟鸣
- 风声
- 脚步声
- 自行车铃声
- 雨声

示例反馈：

```text
噢，我好像听到了鸟鸣。
```

### 7.5 Light Walk

Light Walk 由硬件光照传感器触发。

完成条件初版：

```text
lux > 300
并且 motion = moving / walking
```

小芽反馈：

```text
真好，我又感到活过来了。
```

### 7.6 Local Discovery

Local Discovery 用于记录附近的新发现。

可以包括：

- 新店
- 街角植物
- 树影
- 小动物
- 建筑细节
- 路边变化

当前可以先做静态或 mock 内容，不强求接真实推荐系统。

### 7.7 小芽日记 Diary

Figma 中包含两种日记形态：

```text
流水账
小作文
```

流水账记录事件：

- 什么时候看到阳光
- 什么时候听到声音
- 什么时候拍照
- 什么时候完成任务

小作文由 AI 生成，综合：

- 光照变化
- 声音识别
- 照片识别
- 散步时长
- 任务完成情况

### 7.8 散步地图 Walk Map

散步地图用于展示：

- 拍照位置
- 录音位置
- 光照变化位置
- 小芽状态变化位置
- 任务完成位置

当前可以先用静态地图或模拟地图。

### 7.9 附近 Nearby

Figma 中包括：

- 附近新店
- 附近的新变化
- 附近树友在发现什么

本阶段可以先用 mock 内容。

### 7.10 小芽图鉴 Atlas

图鉴用于展示解锁的小芽类型。

示例：

| 小芽类型 | 解锁条件 |
|---|---|
| 阳光小芽 | 完成一次 Light Walk |
| 雨后小芽 | 雨天或湿度较高时完成散步 |
| 街角小芽 | 完成 Local Discovery |
| 声音小芽 | 完成 Sound Walk |
| 夜晚小芽 | 夜间散步 |

## 12. 对声音识别的最终判断

本对话中明确过：

```text
APP 录音上传 + 后端识别：本次可以做
硬件实时录音 + 实时识别 + 实时播报：放到下一版本
```

原因：

- APP 录音质量更稳定。
- 上传文件更简单。
- 后端调用模型更方便。
- 更适合课程 Demo。
- 硬件端保留声音变化检测即可。

---

## 13. 对本地语音库的最终判断

以当前硬件，有可能把少量语音存到硬件里。

推荐：

- 基础状态语音存硬件本地。
- 每个状态准备 1-3 条短语音。
- 根据状态播放本地语音。

不推荐：

- 把每次 AI 生成的动态语音都永久存到硬件。

推荐分工：

```text
基础状态语音 -> 硬件本地播放
复杂 AI 语音 -> APP / 后端播放
```
