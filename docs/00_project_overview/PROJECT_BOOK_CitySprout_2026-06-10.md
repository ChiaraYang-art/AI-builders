## 1. 项目摘要

出走小芽 City Sprout 是一个挂件+桌搭一体的植物形态 AI 小伙伴。它能通过多种传感器感知自己所处的环境，并用温柔的口吻邀请用户带它出门看真实世界。

解决的问题：当人长期待在室内、被屏幕和日程困住时，往往缺少一个有趣、具体、低压力的出门理由。

项目目前已经形成三条主线：

```text
硬件小芽
  -> AtomS3R + PaHUB + DLight + OLED + ENV-Pro + IMU + Voice Base

Flask 后端
  -> 接收传感器状态，生成小芽文案，维护 latest 状态，处理 walk/photo/audio/diary

Vue App
  -> 展示小芽状态、四类散步任务、照片/录音上传、日记、地图、附近、图鉴、分享等页面
```

## 2. 项目源起与前期构思

### 2.1 更大的母题

项目最早不是直接从“小芽”开始，而是围绕一个更大的问题展开：

> 如何借助 AI 和硬件，鼓励人们离开压抑、屏幕化的日常，重新接触真实世界？
—————我们始终都是从技术出发，但最终落脚点不在技术，而在生活与真实世界。


早期探索过几个方向：

| 方向 | 核心想法 | 后续命运 |
|---|---|---|
| 旧衣改造 / 低门槛实体创造 | 用 AI 降低普通人做实体创作的门槛 | 废弃，但保留了“AI 帮人回到现实材料”的母题 |
| 家用植物说话花盆 | 用传感器和 AI 把植物环境状态转译成人能理解的话 | 启发了“植物人格化表达” |
| Tree Companion / 一棵树的来信 | 认养真实城市树，通过传感器和 AI 生成树信 | 诗意和公共性强，但户外部署、许可、防水、防盗、供电难度高 |
| Tree Scarf / 树围巾 | 通过压力传感器识别拥抱树，灯光回应 | 更适合展览装置和公共空间项目 |

这些早期方案共同留下了三个核心判断：

1. AI 不应只是聊天功能，而应把真实世界的数据翻译成有温度的体验。
2. 硬件的价值在于提供实体陪伴、真实感知和仪式感。
3. 项目不能把用户继续困在 App 里，而要把用户带向阳光、街道、树影、声音和身体行动。

### 2.2 从“认养真实的树”收敛为“可携带小芽”

我们多次比较了“真实树认养”和“可携带 AI 小植物”两个方向。

最终选择出走小芽，是因为它更适合比赛项目 Demo：

- 不需要真实树木认养许可。
- 不需要长期户外部署。
- 不需要防水、防盗、太阳能供电。
- 能用现有 M5Stack 硬件现场演示。
- 能更快打通“感知 -> 表达 -> 行动 -> 记录”的闭环。

因此，项目从：

```text
真实城市树给人写信
```

转变为：

```text
一棵电子小芽邀请人带它出门
```

这不是概念上的退化，而是一次产品化收敛：保留了“人与城市自然重新建立关系”的母题，同时把实现范围缩短到可演示、可制作、可迭代的硬件产品。

## 3. 产品定位与设计理念

### 3.1 产品定位

出走小芽 City Sprout 是一个挂件+桌搭一体的植物形态 AI 小伙伴。它通过光照、声音、移动和环境传感器感知自己是否长期停留在室内，生成低门槛出门请求，引导用户带它去晒太阳、听声音、寻找颜色和发现附近变化等，并陪伴用户一起出门。

### 3.2 目标用户

- 久坐宿舍、教室、工位的学生或年轻上班族。
- 想出门但缺少启动理由的人。
- 不喜欢运动打卡、步数 KPI、健康监督的人。
- 喜欢桌面摆件、电子宠物、可爱硬件的人。
- 喜欢记录生活、分享轻量治愈内容的人。

### 3.3 设计原则

项目在多轮讨论中形成了很清晰的设计边界：

| 原则 | 说明 |
|---|---|
| 不做健康打卡 | 不强调步数、卡路里、KPI，也不责备用户 |
| 不命令用户 | 小芽温柔表达自己的感受，而不是要求用户必须完成任务 |
| 低门槛 | 任务应当 3-15 分钟可完成，可失败、可跳过 |
| 真实世界优先 | AI 和 App 都服务于出门，而不是让用户停留在屏幕里 |
| 硬件有必要 | 光照、移动、声音、OLED、彩屏、语音共同建立“带它出门”的实体感 |
| AI 重要性 | AI 的价值：1.把 lux、motion、照片、声音等转译成小芽语言和日记；2.赋予小芽个性化的人格，与用户逐渐建立默契 |
| 规则保稳定 | 在演示demo中，高频状态用规则和文案库，复杂照片/声音/日记再交给大模型 |

### 3.4 核心体验闭环

```text
小芽长期待在室内
  ↓
光照低 / 静止 / 声音单调
  ↓
小芽变蔫，提出低压力出门请求
  ↓
用户带小芽出门
  ↓
硬件检测光照、移动、声音和环境变化
  ↓
App 开始 Light / Color / Sound / Local 任务
  ↓
用户拍照、录音、散步
  ↓
后端生成反馈、日记、图鉴解锁和成长记录
  ↓
用户获得一段“我和小芽一起出门”的记忆
  ↓
小芽个性化成长
```

## 4. 硬件方案

### 4.1 当前硬件清单

| 模块 | 当前作用 |
|---|---|
| M5Stack AtomS3R | 主控、Wi-Fi、彩屏、小芽动画、内置 IMU |
| Atomic Voice Base | 麦克风、扬声器、语音播放 |
| PaHUB | 多个 I2C 模块分线 |
| DLight BH1750 | 光照 lux 读取，是 Light Walk 的核心输入 |
| Unit OLED 1.3 inch | 黑白文字屏，显示状态 UI 和短句 |
| ENV-Pro BME688 | 温度、湿度、气压、空气质量趋势 |
| AtomS3R 内置 IMU | still / active / walking / shaken 判断 |
| 移动电源 / USB-C | 现场供电 |

Atom-Matrix 曾在早期方案中出现，但后来判断第一版不再作为主控使用，因为 AtomS3R 已经有屏幕、IMU 和 Wi-Fi，继续使用双主控会增加通信复杂度。

### 4.2 硬件显示分工

```text
AtomS3R 彩屏
  -> 彩色小芽身体、动画、摇摆、花朵、成长状态

OLED 黑白屏
  -> 状态标题、短句、进度、装饰性 UI
```

这个分工来自 `对话4` 里的实机调试经验：OLED 适合文字和状态，不适合彩色植物图形；S3R 彩屏更适合表现小芽形象。

### 4.3 已完成的硬件能力

当前已经完成或基本形成代码链路的硬件能力包括：

- DLight 光照读取。
- IMU 静止 / 移动 / 散步 / 摇晃检测。
- ENV-Pro 温湿度等环境数据读取。
- Voice Base 麦克风环境音变化检测。
- Voice Base 扬声器播放测试。
- S3R 彩屏小芽动画。
- OLED 中文状态 UI。
- PaHUB 多模块连接方案。
- `/plant` HTTP 上报。
- LLM 开关轮询。
- 后端 TTS MP3 播放。
- 预设 MP3 兜底播放。
- v5 路演循环。
- v6 成长循环。
- S3R / OLED 状态 SVG 导出。

| 版本目录 | 作用 | 状态 |
|---|---|---|
| `arduino/archive/dual_screen_state_loop/` | 双屏状态轮播视觉测试 | 历史视觉演示 |

### 4.5 v5 与 v6 区别

v5 是传感器场景路演版：

```text
idle -> dark -> need sun -> walk -> sunlight -> city sound
```

适合展示小芽如何在不同环境下改变状态。

v6 是成长循环版：

```text
1 芽 -> 2 苗 -> 3 含苞 -> 4 盛开
```

适合讲述用户多次带小芽出门后，小芽逐渐成长的故事。

## 5. 软件与后端方案

### 5.1 后端架构

当前后端位于：

```text
backend/
```

后端已经从早期单文件 Flask 演进为分层结构：

```text
backend/
  app.py
  sprout_server.py
  config.py
  api/
  ai/
  utils/
  tests/
```

主要职责：

- 接收硬件传感器数据。
- 生成小芽文案。
- 维护最新状态 `/latest`。
- 管理 LLM 开关。
- 生成或提供 TTS 音频。
- 管理 walk session。
- 接收照片和录音。
- 生成散步日记。
- 记录图鉴解锁、成长值、日记历史。

### 5.2 当前后端接口

| 接口 | 功能 | 当前状态 |
|---|---|---|
| `POST /plant` | 硬件上传 state/lux/motion/sound/env，返回小芽文案 | 已实现 |
| `GET /latest` | App 获取最新状态、TTS 状态、active walk、diary、atlas 等 | 已实现 |
| `GET /audio/latest.mp3` | 获取最新 TTS 音频 | 已实现，依赖有效 API Key |
| `GET /audio/library/<file>` | 获取预设 MP3 语音库 | 已实现 |
| `GET/POST /settings/llm` | 控制是否启用大模型 | 已实现，并做 JSON 持久化同步 |
| `POST /walk/start` | 开始一次散步 | 已实现 |
| `POST /walk/photo` | Color Walk 上传照片并识别 | 已实现，VLM 失败时有 fallback |
| `POST /walk/audio` | Sound Walk 上传录音并生成声音摘要 | 已实现，但是真实听音识别仍是轻量/伪识别 |
| `POST /walk/progress` | 更新 Light Walk 晒光进度 | 已实现 |
| `POST /walk/diary` | 完成散步，生成日记 | 已实现，支持 `force_complete` |
| `GET /walk/media/<walk_id>/<file>` | 读取散步媒体文件 | 已实现 |

### 5.3 后端已实现的重要机制

当前代码中已经具备以下能力：

- `latest_message` 维护最新小芽状态。
- JSON 文件 `backend/generated/sprout_state.json` 持久化部分状态。
- `llm_enabled` 支持跨 worker 同步，避免 gunicorn 多 worker 状态不一致。
- 关闭 LLM 时走规则文案，不调用大模型和 TTS。
- `/plant` 生成 speech 后，会写入 active walk 的 speech event。
- Light Walk 有 `LIGHT_SUN_TARGET_SECONDS = 180` 的晒光目标。
- Color Walk 目标已改为 `COLOR_TARGET = 2`。
- Color Walk 至少拍 1 张照片才允许自然完成。
- Light Walk 未达标时可返回 `walk_not_complete`，前端可以选择强制结束。
- `force_complete` 支持演示时跳过未完成条件。
- 完成散步会增加 `walk_count` 和 `growth_delta`。
- 图鉴根据 walk 类型解锁 `Sunny / Sound / Bloom / City Sprout` 等。
- 散步日记会保存到 `diary_history`。

### 5.4 AI 策略

项目讨论中形成了一个成熟策略：

```text
高频基础状态
  -> 规则文案 / 文案库 / 预设 MP3

复杂任务输入
  -> 大模型 / 多模态模型
```

适合规则或文案库：

- idle
- wilted
- need_sun
- sunlight
- walking
- 基础出门建议
- 演示兜底语音

适合大模型：

- Color Walk 图片理解。
- Sound Walk 真实音频识别。
- 散步日记。
- 分享文案。
- 长期个性化总结。

### 5.5 当前 AI 限制

当前已知限制包括：

- 百炼 API Key 在最近一次验证中不可用，真实 LLM 和 TTS 不能完整验证。
- Color Walk 有 VLM 接口，但失败时走固定 fallback。
- Sound Walk 当前 `ai/audio.py` 没有真正读取和理解音频内容，而是根据常见城市散步场景生成标签和总结。
- 日记已能注入 events、photo、audio、light_progress、latest_snapshot，但 prompt 输出还比较基础。

## 7. 制作流程回顾

### 7.1 概念阶段

从硬件清单出发，先判断每个模块可以带来的体验价值：

- 光照 -> 植物是否见到太阳。
- IMU -> 是否被带走。
- 声音 -> 是否听见城市。
- ENV -> 环境变化和日记素材。
- OLED / 彩屏 -> 小芽实体人格。
- Voice Base -> 小芽可以发声。

然后从多个产品方向中选择“AI 出门提醒器”，再将其拟人化为“一棵想出门的 AI 植物”。

### 7.2 PRD 与产品系统阶段

生成了 `PRD_CitySprout_软硬件一体版_2026-05-28.md`，明确：

- 硬件、后端、App 的职责边界。
- 五个主状态：`idle / wilted / need_sun / sunlight / walking`。
- 四类散步任务。
- 首页、日记、地图、Nearby、图鉴、设置等 App 模块。
- P0 / P1 / P2 功能优先级。
- 推荐后端接口。

## 13. 推荐演示叙事

建议课堂或决赛现场这样讲：

1. 我们关注的问题核心是“如何给疲惫的人一个温柔的出门理由”。
2. 小芽长期待在室内，会通过光照、移动和声音感知到自己缺少真实世界。
3. 它不会命令用户完成任务，而是温柔、提议式地表达自己的需要：“我今天还没有见到真正的阳光，我们出去晒三分钟太阳好吗？”
4. 用户可以选择晒太阳、收集颜色、听城市、附近走走等轻量任务。（未来用户可以通过直接和小芽对话选择任务。目前也可以在APP上切换任务）
5. 用户带小芽出门后，硬件会检测到光照、移动等变化；AI实时生成小芽的散步想法
6. 散步结束后，小芽会生成一篇自己的日记，把这次出门变成记忆。
7. 后续小芽会逐渐成长，并解锁不同形态。

> 出走小芽是一棵想见真实世界的 AI 小植物，它用照顾&陪伴的关系，温柔地把人带出房间。

## 15. 商业化路径

### 15.1 商业化核心判断

City Sprout 的商业化不宜只理解为“卖一个 AI 硬件”。硬件本身可以成为入口和情感锚点，但更有想象力的商业价值在于：

```text
可携带小芽硬件
  -> 触发真实出门行为
  -> App 记录用户的附近探索
  -> Local Discovery 推荐好去处
  -> 本地商家获得自然、低打扰的到店机会
```

也就是说，小芽不是普通广告位，而是一个“把用户温柔带到线下”的生活方式入口。

### 15.2 Local Discovery + 本地生活广告

目前最核心的商业化方向，可以围绕 Local Discovery 展开。

用户在小芽的邀请下出门，小芽可以根据位置、时间、天气、用户偏好和当前状态，推荐附近的真实好去处：

- 公园、树荫、小路、河边、校园角落。
- 咖啡店、甜品店、书店、花店、展览、手作空间。
- 大众点评/美团上的高评分本地生活服务。
- 小红书上的附近种草内容。
- 商家购买的“轻量探索任务”广告。

关键是不要让它变成硬广，而是把商家信息转译成小芽的任务语言。

普通广告写法：

```text
附近 XX 咖啡店新品 8 折，点击购买。
```

小芽式推荐：

```text
附近那家咖啡店门口好像有一排绿色小盆栽。我们不一定要买东西，就去看看那片绿色好吗？
```

这样广告不是“消费命令”，而是“城市线索”。

### 15.3 推荐比例机制

你们提出的“普通好去处 / 特定广告建议”比例非常关键。建议设计成一个可调的推荐配比系统：

| 推荐类型 | 建议比例 | 内容来源 | 作用 |
|---|---:|---|---|
| 自然/公共空间推荐 | 40% | 公园、树荫、河边、校园、街角 | 维持产品初心，避免过度商业化 |
| 用户兴趣和历史偏好推荐 | 25% | 用户收藏、历史散步、常去区域 | 提高个性化和留存 |
| 平台内容推荐 | 20% | 小红书附近笔记、美团/大众点评 POI | 提供真实城市内容 |
| 商业广告推荐 | 15% | 付费商家、品牌活动、本地店铺 | 形成收入 |

早期 Demo 可以讲成：

```text
80% 是普通城市探索建议，20% 是商业合作建议。
```

后续商业化时可根据用户接受度调节，例如：

- 普通用户默认广告不超过 15%-20%。
- 会员用户可降低广告比例。
- 商家活动期间可提高特定区域广告比例，但必须标注“合作推荐”。
- 如果用户连续跳过商业推荐，系统自动降低广告频率。

### 15.4 商家为什么愿意付费

商家购买 Local Discovery 的理由不是传统曝光，而是更接近“低压力到店种草”：

| 商家诉求 | City Sprout 提供的价值 |
|---|---|
| 想让附近年轻人知道自己 | 小芽把店铺变成附近探索任务 |
| 想提升到店率 | 用户本来就在散步，推荐路径短 |
| 想有小红书内容 | 用户完成任务后可生成分享卡 |
| 想区别于硬广 | 小芽以故事和场景包装推荐 |
| 想做轻活动 | 商家可发布“找绿色门头”“听一段街角声音”“收集一张店门口树影”等任务 |

适合第一批合作的商家：

- 咖啡店、甜品店、面包店。
- 书店、文创店、花店。
- 展览、艺术空间、手作工作室。
- 校园周边小店。
- 公园、植物园、城市更新街区。
- 注重 ESG / 年轻用户体验的品牌快闪活动。

### 15.5 平台合作模式

如果与美团、大众点评、小红书结合，可以分成三层。

第一层：内容数据接入

- 读取附近 POI、评分、营业时间、距离。
- 读取小红书附近笔记中的热门地点和关键词。
- 生成“适合小芽散步”的候选点。

第二层：任务转译

平台原始内容不直接展示，而是由小芽转译成出门任务：

```text
评分高的咖啡店 -> 去看看门口有没有阳光座位
新展览 -> 去收集一种今天没见过的颜色
公园路线 -> 带小芽找一块会动的树影
花店 -> 去门口看一眼今天的花色
```

第三层：商业投放

- 商家购买 Local Discovery 曝光。
- 平台按点击、收藏、到店、任务完成或分享计费。
- City Sprout 可向平台或商家收取服务费、分成或活动费。

### 15.6 收入模型

可组合几种收入来源：

| 模式 | 谁付费 | 说明 |
|---|---|---|
| 硬件销售 | 用户 | 小芽硬件本体、配件、外壳、联名版本 |
| App 会员 | 用户 | 降低广告、更多日记模板、成长皮肤、年度小芽日记 |
| Local Discovery 广告 | 商家 | 本地店铺购买任务推荐位 |
| 平台分成 | 美团/点评/小红书等 | 为平台导流到内容或 POI |
| 品牌活动 | 品牌方 | 春日散步、城市自然、校园探索等主题活动 |
| B 端空间合作 | 商场、园区、学校、文旅空间 | 打造线下“小芽探索路线” |
| 数据洞察服务 | 商圈/品牌方 | 聚合后的散步偏好、区域热度、任务完成率，需严格匿名化 |

其中最适合项目早期讲清楚的是：

```text
硬件入口 + App 留存 + Local Discovery 商家广告 + 分享传播
```

### 15.7 广告体验边界

商业化一定要守住产品气质，否则小芽会从“陪伴植物”变成“会说话的广告牌”。

建议边界：

- 商业推荐必须标注“合作推荐”或“附近合作点”。
- 不允许用焦虑、优惠倒计时、强促销语气。
- 不允许连续多次推同一商家。
- 不允许把所有任务都导向消费。
- 用户必须可以跳过商业任务。
- 商业推荐也要符合小芽的任务逻辑：光、声音、颜色、附近变化、城市观察。
- 不收集精确个人轨迹用于广告定向，至少早期不要这样讲。

一句话原则：

> 商家只能成为小芽发现城市的一条线索，不能成为小芽存在的目的。

### 15.8 可对外讲的商业化版本

可以在路演里这样概括：

> City Sprout 的商业化不是把广告塞进 App，而是把本地生活服务转译成低压力的城市探索任务。小芽会根据用户状态、位置和偏好推荐普通好去处，也会以可控比例推荐合作商家的轻量任务。商家获得自然到店和内容传播，用户获得真实出门理由，平台获得更温和的本地生活入口。

更短的版本：

> 小芽把本地生活广告从“去消费”改写成“去发现”。

### 15.9 商业化路线建议

建议分三阶段推进：

| 阶段 | 目标 | 做法 |
|---|---|---|
| V0.1 课程展示 | 证明体验成立 | 使用 Mock 商家和 Mock 小红书/点评内容，展示推荐比例机制 |
| V0.2 校园/街区试点 | 验证商家意愿 | 找 3-5 个真实小店做 Local Discovery 任务，统计点击、到店、分享 |
| V0.3 平台合作 | 验证规模化 | 接入 POI 或内容平台 API，做可配置广告比例、商家后台和活动包 |

第一批商业化实验不需要一开始就接大平台，可以先做“人工运营版”：

- 手动选择 10 个附近好去处。
- 其中 2 个是合作商家。
- 小芽以 80/20 比例推荐。
- 记录用户是否愿意去、是否愿意拍照分享、是否反感广告。

这个实验能很快验证商业模型是否成立。

## 17. 总结

出走小芽已经从一个“AI 出门提醒器”的点子，发展成了一个有完整产品叙事、硬件原型、后端接口、Vue App、Figma 视觉资产、验证脚本和多轮文档沉淀的软硬件一体 Demo。

它目前已经实现了课程展示所需的 P0 展示闭环：硬件能感知，后端能汇总和生成表达，App 能展示状态、任务、照片、声音、日记和图鉴。它尚未完成的是生产级稳定性、真实 AI 能力的持续可用、真实平台 Local Discovery、长期账号与记忆系统。

项目下一步不应盲目加更多功能，而应优先把一个最小故事讲稳：

```text
小芽想晒太阳
  -> 用户带它出门
  -> 硬件确认真实世界变化
  -> App 记录这次散步
  -> 小芽写下一篇日记
```

只要这个闭环稳定成立，City Sprout 的设计价值就会非常清楚：它用 AI 与硬件创造了一种不说教、不焦虑、可被照顾的出门理由，让人重新走向真实世界。
